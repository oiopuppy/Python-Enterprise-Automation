# 架构与设计

## 1. 形状

这是一个**单进程批处理 CLI**：一次调用、一份输入、一份输出、一个退出码。没有常驻服务、没有数据库、没有消息队列。所有「架构」问题都是围绕这个形状展开的。

```
CLI (argparse)
   │
   ├── AuditEngine.run()            ← 编程式调用也走这里
   │      ├── data.reader       读 Excel
   │      ├── core.validator    列校验 + 逐行质量校验
   │      ├── audit.reconciler  逐行对账 + 汇总
   │      └── audit.reporter    四表报告
   │
   └── utils.config / utils.logger / models.claim
```

## 2. 分层与依赖方向

```
┌─────────────────────────────────────────────┐
│ main.py           入口层：参数、退出码、日志  │
├─────────────────────────────────────────────┤
│ core/engine.py    编排层：串起四步           │
├─────────────────────────────────────────────┤
│ audit/            reconciler / reporter      │
│ core/             calculator / validator     │
│ data/             reader / writer / generator│
├─────────────────────────────────────────────┤
│ models/claim.py   领域模型（Pydantic）        │
├─────────────────────────────────────────────┤
│ utils/            config / logger / exceptions│
└─────────────────────────────────────────────┘
```

约束只有一条：**依赖只能向下，不能回指**。

- `models` 不 import `core`（`ClaimRecord.calculate_payout` 是唯一例外，用函数内导入规避循环）；
- `utils` 谁都可以用，但它不 import 任何业务模块；
- `main` 只做参数、日志、异常到退出码的映射，不写业务逻辑；
- 唯一允许「横穿」的是 `core/engine.py`，它本来职责就是编排。

## 3. 模块职责

| 模块 | 职责 | 不做什么 |
| --- | --- | --- |
| `main.py` | 解析参数、初始化日志、调用引擎、把异常映射成退出码 | 不读文件、不算金额 |
| `core/engine.py` | 串起「读 → 校验 → 对账 → 报告」 | 不处理 CLI、不写日志格式 |
| `core/calculator.py` | 赔付公式的**唯一实现** | 不做校验、不碰 DataFrame |
| `core/validator.py` | 列校验、逐行质量校验、跨字段规则提示 | 不阻断对账（除缺列） |
| `data/reader.py` | Excel → DataFrame，包装 IO 异常 | 不做业务校验 |
| `data/writer.py` | DataFrame → Excel，统一列宽 | 不决定报告结构 |
| `data/generator.py` | 生成模拟数据，可注入差异 | 不参与对账 |
| `audit/reconciler.py` | 构造记录、对账、收集解析失败、汇总 | 不写文件 |
| `audit/reporter.py` | 组织 4 个 sheet、设置数字格式 | 不算金额、不改状态 |
| `models/claim.py` | `ClaimRecord` / `AuditSummary` 字段与校验 | 不做 IO |
| `utils/config.py` | 三级配置、路径解析、参数合法性 | 不创建目录 |
| `utils/logger.py` | 日志配置（惰性）、审计追溯、降级 | 不在 import 时建文件 |
| `utils/exceptions.py` | 四类异常 + 错误码 | 不处理异常 |

## 4. 数据流

```
xlsx
  │  read_excel(dtype_backend="numpy_nullable")
  ▼
DataFrame ──► validate_dataframe() ──► list[DataValidationError]
  │                                      │
  │                                      └──► 报告 sheet「数据质量问题」
  ▼
reconcile_dataframe()
  ├─ 逐行 ClaimRecord.model_validate(...)   ← 失败 → parse_errors（不丢弃）
  ├─ record.reconcile()                     ← Decimal 重算 + 容差比较
  └─ AuditSummary（source/total/parse_error/matched/unmatched/match_rate/金额合计）
  ▼
generate_report()
  ├─ sheet 审计摘要（数值 + 单位）
  ├─ sheet 对账明细（含解析失败行）
  ├─ sheet 异常数据（异常 + 解析失败）
  └─ sheet 数据质量问题（字段级 + 无法解析）
```

## 5. 关键决策

### D-01 金额全程 `Decimal`

**背景**：`float` 在 `0.1 + 0.2` 上就会失真，理赔金额动辄百万，分位误差会被放大。
**选择**：从 Excel 读取开始 `Decimal(str(...))`，计算、比较、写报告都用 `Decimal`，`ROUND_HALF_UP` 两位。
**代价**：pandas 不能直接算 `Decimal` 列，逐行构造成本高；报告明细里的金额列是字符串（保留原值），摘要是真正的数值。

### D-02 解析失败不丢行

**背景**：早期版本 `except ValueError: continue`，结果报告里少行，一致率分母也变了，审计上不可接受。
**选择**：解析失败收集进 `summary.parse_errors`，明细里也追加一行「解析失败」，并保证 `source_records = total_records + parse_error_records`。
**代价**：报告里存在空单元格行，样子不好看；但「少掉的几行去哪了」永远能回答。

### D-03 跨字段业务规则只提示、不抛错

**背景**：曾尝试在 `ClaimRecord` 上用 `model_validator` 拒绝「实际赔付 > 报案金额」。结果测试里故意造的差异行被当成解析失败丢掉，审计目标反而失效。
**选择**：模型层只做字段级校验；跨字段规则放到 `validator`，作为「数据质量问题」提示。
**代价**：模型本身不保证业务自洽，调用方必须看校验结果。

### D-04 日志惰性初始化

**背景**：模块级 `audit_logger = AuditLogger()` 让 `import insurance_audit` 就创建 `logs/`，只读目录、容器挂载、`--help` 全都崩。
**选择**：库模块只 `get_logger()`（不配 handler）；入口 `main()` 最先调 `setup_logging()`；审计日志改 `get_audit_logger()` 惰性单例；文件不可写时降级为仅控制台。
**代价**：库被别的程序当模块用时，日志不自动配好，需要调用方自己 `setup_logging()`——这是对的。

### D-05 `PROJECT_ROOT` 显式化

**背景**：`Path(__file__).resolve().parents[3]` 在源码树里指项目根，在容器里指 `/usr/local/lib/python3.11`，`data/`、`reports/`、`logs/` 全跑偏。
**选择**：优先读 `PROJECT_ROOT` 环境变量，Dockerfile 里固定 `/app`。
**代价**：多一个必设变量；已经写进 README 和 `.env.example`。

### D-06 赔付公式只留一份

**背景**：`calculator.calculate_payout` 与 `ClaimRecord.calculate_payout` 各写一遍，改一处漏一处。
**选择**：`ClaimRecord.calculate_payout` 委托核心函数；因 `calculator` 需要 `ClaimRecord` 做类型标注，用函数内导入避免循环。
**代价**：每次计算多一次函数内 import（CPython 有缓存，可忽略）。

### D-07 退出码用 `if/else` 而不是提前 `return`

**背景**：`main()` 里 `if not check_environment(): return` 会跳过文末 `sys.exit(exit_code)`，进程退出码恒为 0，流水线永远绿。
**选择**：`exit_code` 变量贯穿始终，末尾统一 `sys.exit(exit_code)`；异常按类型映射到不同退出码。
**代价**：无。

### D-08 标准 src 布局

**背景**：v1 把模块散在仓库根，测试 import 依赖工作目录。
**选择**：`src/insurance_audit/` + `pyproject.toml`（setuptools），editable 安装后任何目录都能跑。
**代价**：必须 `pip install -e .`，不能直接 `python main.py`。

### D-09 CI 用 3.9 + 3.12 双版本

**背景**：`requires-python >=3.9`，但早期 CI 只测 3.11/3.12，3.9 上的 `X | Y` 注解、`datetime.UTC` 之类问题发现不了。
**选择**：测试矩阵 `3.9`、`3.12`；`mypy` 分析目标用 3.10（mypy 1.20 起不支持 3.9 目标），3.9 的运行时兼容性由测试矩阵兜底。
**代价**：CI 时间翻倍；换来的是「声明支持就真的能跑」。

### D-10 删掉 CLI 项目不需要的依赖

**背景**：`prod` 组挂着 `gunicorn` / `supervisor`，但项目没有 Web 服务。
**选择**：删除；`requirements.txt` 与 `pyproject.toml` 对齐。
**代价**：无。

## 6. 扩展点

| 想做的事 | 改哪里 |
| --- | --- |
| 支持 CSV / 数据库输入 | 新增 `data/xxx_reader.py`，在 `engine.run()` 里选择 reader |
| 换一种赔付规则 | 只改 `core/calculator.py`，模型层自动跟随 |
| 增加报告 sheet | 改 `audit/reporter.py`，注意保持摘要恒等式 |
| 增加校验规则 | `core/validator.py` 的 `validate_row`，加进 `COLUMN_CONSTRAINTS` 或独立步骤 |
| 对接调度系统 | 用退出码；或直接调 `AuditEngine.run()` |
