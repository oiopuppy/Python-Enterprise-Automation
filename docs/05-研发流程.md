# 研发流程

这是单人项目的流程，不套团队那套（RACI、评审人矩阵、双人签字都没有）。保留的只有**能防自己犯错的部分**。

## 1. 分支模型

```
main       ●──────────────●──────────────  ← 只放可交付版本，打 tag
            \            /
develop      ●──●──●──●──●──●──●──●──────  ← 日常集成，CI 始终绿
              \    \     \
feature/x      ●────●     ●                 ← 短期分支，一个 PR 一条
fix/y                      ●────●
```

- `main`：每个提交都是可交付状态，带版本号 tag。**不直接 push**。
- `develop`：集成分支，所有 PR 合到这里。始终保持全部门禁绿。
- 工作分支：从 `develop` 拉，命名 `feat/xxx`、`fix/xxx`、`chore/xxx`、`docs/xxx`、`test/xxx`。完成即删。

唯一的例外是 CI 引导：`develop` 从 `main` 拉出时，`main` 上的 workflow 只监听 `main`，导致 `develop` 的 PR 不触发流水线。所以第一次先在 `develop` 上直接落一个 `ci: ...` 提交（`0d03014`）把 `pull_request` 的 base 分支补上。这类「引导提交」只在仓库初始化阶段允许，之后一律走 PR。

## 2. 提交信息

Conventional Commits：

```
<type>(<scope>): <subject>
```

| type | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修 bug |
| `refactor` | 不改行为的重构 |
| `test` | 只动测试 |
| `docs` | 只动文档 |
| `chore` | 构建、依赖、配置 |
| `ci` | 流水线 |

subject 中文、动词开头、不超过 50 字；正文写「为什么」，不写「改了什么」（diff 已经说明了）。

本次实际提交（可作为范例）：

```
fix(audit): 解析失败不再静默丢行，退出码按审计结果返回
chore(ci): 修复质量门禁并统一到 Python 3.9
fix(runtime): 日志惰性初始化并支持显式 PROJECT_ROOT
```

## 3. PR 流程

1. 从 `develop` 拉分支，小步提交；
2. 本地四道门禁先跑绿：`ruff check` → `ruff format --check` → `mypy --strict` → `pytest`，外加三个 `scripts/check_*.py`；
3. `git push -u origin <branch>`，开 PR，base 选 `develop`，先转 **Draft**（没写完、没自测完就别标记 Ready）；
4. PR 描述按模板填：**动机 / 改动 / 验证 / 风险 / 不在本 PR 范围**；
5. 等 CI 全绿；
6. 自己审一遍 diff（单人项目没有第二个人，但「隔一天再看」同样有效）；
7. 在 PR 里留一条 GO 记录再合并：`GO / HEAD=<完整 SHA> / CI=GREEN / REVIEW=自查 / DOD=PASS`——万一以后要回溯「当时为什么敢合」，这条记录比时间线有用；
8. `gh pr merge --merge --delete-branch` 合入 `develop`。

GitHub 不允许 PR 作者 approve 自己的 PR（`422 Review Can not approve your own pull request`），所以流程上是「CI 全绿 + 自查记录 + 合并」，不伪造 review 状态。

PR 模板见 `.github/pull_request_template.md`。

## 4. 版本号

SemVer：`MAJOR.MINOR.PATCH`。

- `MAJOR`：命令行接口/配置项/报告结构不兼容；
- `MINOR`：向后兼容的新能力（如 `--input`）；
- `PATCH`：修复。

当前 `2.0.0`：相对 v1 整体重写（src 布局、Decimal、Pydantic v2、四 sheet 报告、退出码语义），属于不兼容变更，所以直接给 `2.x`。

`pyproject.toml` 的 `version` 是唯一事实源；`CHANGELOG.md` 按版本记录「新增 / 变更 / 修复」。

## 5. 发布

只有版本里程碑才动 `main`：

1. `develop` 上跑完四道门禁与手工清单（见 `04-质量与测试.md`）；
2. 更新 `pyproject.toml` 的 `version` 与 `CHANGELOG.md`，单独一个 `chore(release): vX.Y.Z` 提交；
3. 开 PR：`develop → main`，合并后 `git tag vX.Y.Z`；
4. `gh release create vX.Y.Z`，正文取 CHANGELOG 对应段落；
5. 回到 `develop` 继续开发。

## 6. CI 说明

`.github/workflows/ci.yml` 四个 job：

| job | 做什么 |
| --- | --- |
| 代码质量 | `pip install -e ".[dev]"` → 三个 `scripts/check_*.py` → `ruff check` → `ruff format --check` → `mypy --strict` |
| 安全扫描 | `bandit -r src/ -ll` + `pip-audit -r requirements.txt --strict` |
| 测试 | 矩阵 `3.9` / `3.12`，`pytest --cov=src/insurance_audit` |
| 构建 | `python -m build`，校验产物可安装 |

触发条件：push 到 `main`/`develop`，以及以 `main`/`develop` 为 base 的 PR。lint 不过，后面的 job 不再浪费算力。

流水线层面的约定：

- **concurrency**：同一分支的新 push 会取消上一次还在跑的流水线（`cancel-in-progress: true`），避免连续 amend 时排队；
- **最小权限**：workflow 只有 `permissions: contents: read`，不需要写权限；纯文档提交也不跳过 CI——链接、`.env.example`、版本号这些检查恰恰只在文档改动时最容易出问题；
- **action 固定 SHA**：`actions/checkout`、`setup-python`、`upload-artifact` 都钉到 commit SHA（行尾注释标主版本），防止 tag 被移动到别的提交；
- **Dependabot**：`.github/dependabot.yml` 每周检查 pip 依赖与 GitHub Actions，开 PR 交给 CI 验证。

## 7. 当前仓库状态

- 默认分支 `main`，开发分支 `develop`；
- `main` 与 `develop` 都开了分支保护：5 个 CI 检查必须全绿（strict）、禁止 force push、禁止删除；`enforce_admins=false` 保留管理员兜底能力；
- 无 CODEOWNERS、无强制 review（单人项目，GitHub 也不允许自审自批）。

## 8. 踩过的坑

留在这里，下次别再犯：

- **PR 事件用的是 base 分支的 workflow**：新分支的 `ci.yml` 不会对比它自己的 PR 生效，所以改 CI 需要先让 base 分支拥有新定义。
- **`git add -A` 必须和 `commit` 在同一条命令里确认成功**：曾经 `git add -A` 因命令拼接出错没执行，`git commit -F` 只提交了一个文件，其余改动随后被 `git checkout -- .` 抹掉，全部重做。现在提交后必看 `git show --stat HEAD`。
- **PowerShell 不支持 heredoc**：提交信息写到临时文件再 `git commit -F`。
- **`mypy --strict` 要装依赖再跑**：只装 `mypy` 不装 `pydantic`，`BaseModel` 会被当成 `Any`，报一堆假阳性。
