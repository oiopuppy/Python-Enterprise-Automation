# 详细设计

本文是「对接方和排障方」的接口手册：输入长什么样、输出长什么样、失败时拿到什么。

## 1. 输入数据契约

### 1.1 文件

| 扩展名 | 说明 |
| --- | --- |
| `.xlsx` / `.xlsm` | 原生支持 |
| `.xls` | 需要 `xlrd`（`pip install xlrd`），否则报错并提示另存为 `.xlsx` |
| `.csv` / `.tsv` / `.txt` | 自动探测编码（`utf-8-sig` → `utf-8` → `gb18030`）与分隔符（`,` / `\t` / `;` / `\|`） |

- Excel：默认读第一个 sheet，可用 profile 的 `sheet` 指定名字或序号；sheet 不存在时报错并列出文件里实际有哪些 sheet；
- CSV：默认自动探测编码；也可用 profile 或 `encoding` 参数显式指定（如 `gb18030`）；
- 表头默认在第一行；客户导出常带一行说明，用 profile 的 `skiprows` 跳过，例如 `skiprows: 1` 表示表头在第 2 行；
- 空文件/空表：返回空摘要（各计数为 0），报告正常生成；
- 不支持的后缀（如 `.json`）直接报错，不再「只 warning 然后按 Excel 硬读」。

### 1.2 列

| 列名 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `保单号` | 文本 | 是 | 以 `INSURANCE_POLICY_PREFIX`（默认 `CL`）开头，其后全是数字；非空 |
| `客户姓名` | 文本 | 是 | 非空 |
| `报案金额` | 金额 | 是 | `INSURANCE_MIN_CLAIM_AMOUNT ~ INSURANCE_MAX_CLAIM_AMOUNT`；最多两位小数 |
| `免赔额` | 金额 | 是 | `0 ~ 99999999.99`；最多两位小数 |
| `赔付比例` | 小数 | 是 | `0 ~ 1`（`0.8`，不是 `80`）；最多两位小数 |
| `实际赔付金额` | 金额 | 是 | `0 ~ 99999999.99`；最多两位小数 |

缺列 → `InvalidColumnError`（`DAT-0102`），进程退出码 `1`，不生成报告。

**表头别名**：读取后会先去掉 BOM、全角空格与首尾空格，再把常见写法归一成标准列名（标准列优先；同一字段出现多列时只认先出现的一列，其余保留原名并告警）：

| 标准列 | 可接受的别名 |
| --- | --- |
| `保单号` | 保单编号、保单ID、保单编码、投保单号、policy_id |
| `客户姓名` | 客户名称、被保险人、投保人、客户 |
| `报案金额` | 报案额、索赔金额、赔款金额、出险金额 |
| `免赔额` | 免赔、免赔金额、扣除额 |
| `赔付比例` | 赔付率、给付比例、赔偿比例 |
| `实际赔付金额` | 实际赔付、实赔金额、已赔付金额、实际赔偿金额 |

缺列报错会同时列出「已识别的列」「缺失的列」「期望的列名」，方便客户对照修改。
标准模板在 `data/templates/标准台账模板.xlsx`，表头与上表一致，有测试保证两者不漂移。

**映射 profile**：客户原始表列名完全对不上别名表时（英文列名、自定义叫法），不用改源表，写一份 profile 指过去即可：

```json
{
  "role": "ledger",
  "encoding": "gb18030",
  "skiprows": 1,
  "columns": {
    "保单号": "policy_no",
    "客户姓名": "insured_name",
    "报案金额": "claim_amount",
    "免赔额": "deductible",
    "赔付比例": "payout_ratio",
    "实际赔付金额": "actual_payout"
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `columns` | 标准字段 → 源列名；键必须是标准字段（15 个之一），写错启动即报错 |
| `role` | `ledger` / `payment` / `core`，多源对账预留：本版只做校验与草稿输出，引擎不消费 |
| `primary_key` | 主键字段（默认空 = 未配置，交给调用方用默认键），须是标准字段；本版只做校验与草稿输出，引擎去重仍按保单号 |
| `timeline` / `date_formats` | 时间轴字段与日期格式顺序，默认支持 `2026-03-05`、`2026/03/05`、`20260305`、`2026年3月5日` |
| `amount_unit` | `yuan`（默认）或 `wan`；`wan` 时金额列自动 ×10000 |
| `sheet` / `encoding` / `skiprows` | Excel 选 sheet、CSV 指定编码、跳过表头前的说明行 |
| `tolerance_absolute` / `tolerance_ratio` | 该 profile 的容差覆盖，留空用全局配置；对账时逐行生效（`max(absolute, 报案金额 × ratio)`），日志会打印「profile 容差生效」 |

- profile 声明的列找不到 → 报错写明**源列名、标准字段、表头行号、文件实际列名**，例如：`profile 声明的列在 文件 客户台账.csv 里找不到: 'policy_no'（标准字段 保单号）；表头位于第 2 行；文件实际列名: [...]`；
- profile 里引用的源列在文件中出现多次时，取先出现的一列；映射目标与已有标准列撞名时保留先出现的那一列，其余列保留原名并在 `audit.log` 里告警（「表头冲突」），不会产生重复标准列；
- 模板按 profile 的 `skiprows` 补说明行、CSV 按 profile 的 `encoding` 写，填完可直接回读（`No columns to parse from file` 这类纯表头文件按空表处理）；
- 不配 profile（或用默认 profile）时行为与 v2.0.0 完全一致：只认 6 个标准中文列。

**标准模型 v2 的扩展字段**：`赔案号`、`被保险人`、`保额`、`案件状态`、`收款账号哈希`、`报案日期`、`受理日期`、`核定日期`、`支付日期`。它们是**可选**的：台账里有就带进模型，没有不影响对账。

**读取层工具**（`python -m insurance_audit.data.reader`）：

| 命令 | 作用 |
| --- | --- |
| `--print-template --out 模板.xlsx` | 生成 6 列标准模板；加 `--full` 生成 15 列 v2 模板；`--format csv` 出 CSV（带 BOM，Excel 打开不乱码） |
| `--profile X.json --print-template` | 按 profile 的源列名生成「客户自己的模板」 |
| `--init-profile profiles/profile.json --from 客户台账.csv --skiprows 1` | 按实际表头自动猜列，生成 profile 草稿 |
| `--inspect 客户台账.csv --skiprows 1` | 看编码、分隔符、列名、行数（排障第一站） |

生成后用 `DATA_PROFILE=profiles/profile.json` 指过去即可，不用改 `main.py` 的参数。

### 1.3 允许的脏数据（进报告、不阻断）

| 情况 | 结果 |
| --- | --- |
| 某行金额为空 / 不是数字 | 该行 `解析失败`，进异常表与明细，不计入一致率 |
| 金额超过两位小数 | 「数据质量问题」提示，**仍参与对账**（按原值计算） |
| 赔付比例 `> 1` | 「数据质量问题」提示，仍参与对账 |
| 保单号前缀/格式不符 | 「数据质量问题」提示，仍参与对账 |
| 实际赔付 > 报案金额 | 「数据质量问题」提示，仍参与对账（这正是要审计的差异） |
| 实际赔付为 0 但应赔 > 0 | 「数据质量问题」提示，仍参与对账 |

原则：**格式问题不阻断业务判断**；只有「无法转成数字」才判定为解析失败。

## 2. 输出报告契约

一个 Excel，固定 4 个 sheet。

### 2.1 审计摘要

三列：`审计项目` / `数值` / `单位`。

| 审计项目 | 单位 | 说明 |
| --- | --- | --- |
| 审计时间 | — | `YYYY-MM-DD HH:MM:SS` |
| 读取总行数 | 条 | Excel 数据行数（不含表头） |
| 成功解析 | 条 | 能构造成 `ClaimRecord` 的行 |
| 无法解析 | 条 | 解析失败行 |
| 重复保单组数 | 组 | 同一保单号出现 ≥2 次的组数（只提示，不删行） |
| 一致记录数 | 条 | `|差异| < 容差`（容差见 §5.1） |
| 异常记录数 | 条 | `|差异| >= 容差` |
| 轻微差异 | 条 | 异常中级别为「轻微」的记录数（≤ 1 元） |
| 一般差异 | 条 | 异常中级别为「一般」的记录数（1~100 元） |
| 重大差异 | 条 | 异常中级别为「重大」的记录数（≥ 100 元） |
| 一致率 | % | `一致 / 成功解析 × 100` |
| 总报案金额 | 元 | 仅成功解析行 |
| 总原始赔付 | 元 | 仅成功解析行 |
| 总系统核算 | 元 | 仅成功解析行 |
| 总差异金额 | 元 | 各异常行差异之和 |
| 输入文件 SHA256 | — | 输入文件内容哈希，证明审的是哪份文件 |
| 输入文件字节数 | 字节 | 输入文件大小 |
| 工具版本 | — | 生成本次报告的工具版本 |
| Python 版本 | — | 运行时 Python 版本 |
| 默认免赔额 | 元 | 本次生效的默认免赔额 |
| 默认赔付比例 | % | 本次生效的默认赔付比例 |

恒等式（测试会校验）：

```
读取总行数 = 成功解析 + 无法解析
成功解析   = 一致 + 异常
```

金额行写入真正的数值单元格，`#,##0.00` 格式；百分比行 `0.00"%"`。

### 2.2 对账明细

| 列 | 类型 | 说明 |
| --- | --- | --- |
| 保单号 | 文本 | |
| 客户姓名 | 文本 | |
| 报案金额 | 数值 | 2 位小数显示 |
| 免赔额 | 数值 | |
| 赔付比例 | 数值 | `0.00%` 格式 |
| 原始赔付金额 | 数值 | 台账里的值 |
| 系统核算金额 | 数值 | 重算值 |
| 差异金额 | 数值 | 绝对值 |
| 审计状态 | 文本 | `一致` / `异常` / `解析失败` |
| 差异级别 | 文本 | `一致` / `轻微` / `一般` / `重大` / `—`（解析失败） |

解析失败的行也在内，金额列留空、状态为 `解析失败`、级别为 `—`。
重大/一般/轻微行在「差异级别」单元格上分别用红/橙/黄底色标出；「差异金额」另有条件格式（`ABS(差异) > 重大阈值` 红、`> 轻微阈值` 黄），改阈值后 Excel 会按新规则自动重算。

四个 sheet 统一：冻结首行（`A2`）、开启自动筛选、横向打印并设置「每页重复标题行」，几千行明细翻页时表头不丢。

金额与比例写入真正的数值单元格（`#,##0.00` / `0.00%` 格式），可以直接筛选、求和。
Excel 只是展示层：逐分精确核对以 `系统核算金额` 为准，重算在 `Decimal` 下完成。

### 2.3 异常数据

`审计状态 ∈ {异常, 解析失败}` 的行，列与明细相同。

### 2.4 数据质量问题

一行里的所有问题都会记录，不会因为第一个问题就跳过后续检查。

| 列 | 说明 |
| --- | --- |
| 问题类型 | `字段校验` / `重复保单` / `跨行不一致` / `无法解析` |
| 问题代码 | 见下表，可直接筛选、统计 |
| 行号 | Excel 行号（表头是第 1 行，数据从 2 开始） |
| 字段 | 出问题的具体列名；整行失败为 `整行` |
| 原因 | 人类可读的原因（重复保单会列出该组全部行号与金额合计） |

| 问题代码 | 含义 |
| --- | --- |
| `EMPTY` | 必填值为空 |
| `FORMAT` | 格式不合法（金额/比例不是数字，保单号前缀不对） |
| `RANGE` | 数值超出允许范围 |
| `PRECISION` | 金额超过 2 位小数 |
| `CROSS_FIELD` | 行内跨字段不一致（实际赔付 > 报案金额等） |
| `DUPLICATE_POLICY` | 同一保单号在多行重复出现 |
| `CUSTOMER_MISMATCH` | 同一保单号对应了多个客户名 |
| `PARSE_ERROR` | 整行无法解析成 `ClaimRecord` |

这些问题只提示、不阻断对账；重复行不删不合并，照常参与对账。

### 2.5 JSON 摘要（`--json` / `--json-out`）

加 `--json` 时，摘要 JSON 输出到 **stdout**（日志改走 stderr，stdout 保持纯 JSON，可直接管道消费）；加 `--json-out PATH` 时，同一份摘要同时落盘。两者可以一起用，也可以只用一个：

```bash
insurance-audit --json > out.json                     # 管道/重定向
insurance-audit --json | jq .summary.match_rate       # 直接在流水线里取字段
insurance-audit --json-out reports/2026-11.json        # 顺便落盘
```

```json
{
  "tool_version": "2.0.0",
  "generated_at": "2026-11-10 20:00:00",
  "input": {
    "path": "data/claims.xlsx",
    "rows": 10000,
    "sha256": "3f786850e387550fdab836ed7e6dc881de23001b..."
  },
  "output": {
    "path": "reports/report.xlsx"
  },
  "summary": {
    "source_records": 10000,
    "total_records": 10000,
    "parse_error_records": 0,
    "matched_records": 9084,
    "unmatched_records": 916,
    "minor_records": 120,
    "normal_records": 796,
    "material_records": 0,
    "match_rate": 90.84,
    "total_claim_amount": "25457485.00",
    "total_actual_payout": "16172086.37",
    "total_calculated_payout": "16172059.79",
    "total_discrepancy": "10494.26"
  },
  "parse_errors": [],
  "quality_issues": [],
  "execution_time": "2.70s"
}
```

约定：

- 金额字段在 JSON 里是字符串，避免 `float` 丢精度；
- `input.sha256` 是输入文件哈希，用于审计留痕；`input.rows` 是读取总行数（含解析失败行）；
- `parse_errors` 元素为 `{row, policy_id, reason}`；`quality_issues` 元素为 `{row, field, code, reason}`，与报告的「数据质量问题」一一对应（含重复保单与跨行不一致）；
- 明细不写进 JSON（大文件会失控），完整明细看 Excel 的「对账明细」sheet；
- 退出码语义不变，JSON 只是附加产物。

### 2.6 审计清单（`--manifest`）

`--manifest PATH` 额外输出一份 JSON 审计清单，用于归档与复核：证明「审的是哪份文件、用的什么版本与参数」。

```json
{
  "tool_version": "2.0.0",
  "python_version": "3.9.13",
  "generated_at": "2026-11-12T00:17:37",
  "input": {
    "path": "data/claims.xlsx",
    "bytes": 7025,
    "sha256": "888ef9dee2197d952d45622637cf9ac605939ed87aa3e4d2e1289538e5ac226f",
    "rows": 50
  },
  "output": {"path": "reports/report.xlsx"},
  "config": {
    "default_deductible": "500",
    "default_ratio": "0.80",
    "decimal_places": 2,
    "policy_prefix": "CL",
    "min_claim_amount": "0.01",
    "max_claim_amount": "99999999.99"
  }
}
```

约定：

- 同一输入文件两次运行，除 `generated_at` 外清单完全一致；
- 只记录业务配置，不写 `.env` 中的账号、令牌等敏感值；
- 输入哈希、工具版本、Python 版本同样写进报告「审计摘要」sheet 和 `logs/audit_trail.log` 的 `AUDIT_COMPLETE` 事件；
- `bytes` 是输入文件字节数，`sha256` 是完整 64 位十六进制哈希；输入文件改 1 个字节哈希即变化。

### 2.7 多源对账（台账 ↔ 支付流水）

单表复核只能回答「这一笔算得对不对」，回答不了「台账记了 100 笔、实际只付了 97 笔」。`audit/crosscheck.py` 补这一层。

**输入**：两边的 DataFrame（已过了读取层与 `normalize_columns`）+ 可选 profile。按键匹配，键的优先级是：

1. 显式传入的 `keys`；
2. profile 里显式写了非空的 `primary_key` —— 写成 `["保单号"]` 也可以；空元组/不写表示「未配置」，回落默认键。不用「是否等于默认值」当哨兵：默认值本身就是单键，那样写 `["保单号"]` 会被当成没配而跳过，只改容差的 profile 也会把主键悄悄降成单键；
3. 默认键 `保单号 + 赔案号`；
4. 缺列（profile 声明的键、或默认键里的任一列）→ `InvalidColumnError`，消息里写清缺哪一列；**不降级成单键**。缺一个键就悄悄按保单号汇总，会把「配置问题」伪装成「金额对不上」，比报错更危险。

**分组**：同一主键的多行先合并成一组再比金额 —— 这正是一个赔案多次支付（退票重付、分期打款）的形态。

**主键归一**：匹配前把键转成文本并统一写法 —— `Float64` 空值列产生的 `12345.0` 与 `12345` 视为同一个键，前导零 `012345`、整数与文本、长数字都有回归用例守住。展示列保留文件里的原始写法，不做归一。键以 tuple 传递，不再拼成 `" / "` 字符串再拆开（键本身含分隔符会串列）。

**四类结果**（`对账结果` 列）：

| 结果 | 含义 | 典型场景 |
| --- | --- | --- |
| `matched` | 两侧都有，金额在容差内，状态不冲突 | 正常 |
| `amount_diff` | 两侧都有但金额差超容差 | 少付、多付、算错 |
| `ledger_only` | 台账有、流水无 | 只记未付 |
| `payment_only` | 流水有、台账无 | 账外赔付、串户 |
| `status_diff` | 金额对得上但状态冲突 | 台账已结案但流水退票；或反之，台账退票但流水已赔付 |

匹配形态写在 `匹配类型` 列：`一对一` / `一对多` / `多对一` / `多对多` / `台账单边` / `流水单边`。

`状态一致` 列只有两侧都有行时才给「是」/「否」；单边行（台账单边、流水单边）只有一侧有状态，谈不上一致，输出 `—`。整个状态检查被 `status_field=None` 关掉时同样是 `—`。

**恒等式**：`Σ台账金额 == Σ流水金额 + Σ差异金额`。`差异金额` 带符号（台账 − 流水），所以多付是负、少付是正。左边的两侧合计是**逐行原始金额独立求和**的，右边的差异是逐组差值累加 —— 两个来源分开算，分组漏行或重复计数才会让 `identity_gap` 不为 0；若拿逐组差值回头验自己，这个等式按构造恒成立，校验等于没有。非 0 时 `identity_holds = False` 并打 error 日志。全部用 `Decimal` 累计，不经过 `float`。

**脏数据**不抛异常，进 `issues` 并标原因：

| 原因 | 含义 |
| --- | --- |
| `主键为空` | 主键任一列为空 —— 该行不参与对账，但仍计入原始行数 |
| `金额不可用` | 空值、NaN、非数字文本 |
| `重复主键` | 同侧出现多行、**且金额完全相同** —— 不等额的分期打款是正常形态，只写进「说明」列；同额多笔才当重复记账嫌疑报上来 |

**已知边界**：这一层目前只作为库接口提供，还没接进报告 sheet 与 CLI（`main.py` / `engine.py` / `reporter.py` 由别的线在改）。日期窗口、状态映射表也还没做，`profile.role` 仍是占位。

## 4. 退出码与错误码

### 4.1 退出码（进程级）

| 码 | 常量 | 触发条件 |
| --- | --- | --- |
| `0` | `EXIT_OK` | 审计完成，且未触发 `--fail-on` 闸门 |
| `1` | `EXIT_AUDIT_ISSUE` | 触发 `--fail-on` 闸门 / 输入文件不存在 / 业务性数据异常 |
| `2` | `EXIT_SYSTEM_ERROR` | `SystemException`（IO、配置） |
| `3` | `EXIT_SECURITY_ERROR` | `SecurityException` |
| `9` | `EXIT_BUSINESS_ERROR` | 其他 `InsuranceAuditError` |
| `99` | `EXIT_UNEXPECTED` | 未捕获异常 |

闸门策略（`--fail-on`）：

| 取值 | 何时退出 1 | 适用场景 |
| --- | --- | --- |
| `any`（默认） | 有任何对账异常或解析失败 | v2.0.0 行为，最严格 |
| `material` | 只有「重大差异」（≥ `INSURANCE_MATERIAL_THRESHOLD`） | 1 分钱噪声不该卡住流水线 |
| `parse-error` | 只有解析失败 | 只关心台账能不能读 |
| `none` | 永不因审计结果退出 1（系统错误仍按 2/3/99） | 只出报告、不阻断 |

### 4.2 错误码（异常级）

`InsuranceAuditError` 的 `error_code` 为 `前缀-四位数字`，并会拼进异常消息 `[BIZ-0101] ...`。

| 错误码 | 异常类 | 含义 | 退出码 |
| --- | --- | --- | --- |
| `ERR-0000` | `InsuranceAuditError` | 基类默认 | `9` |
| `BIZ-0001` | `BusinessException` | 业务异常基类 | `9` |
| `BIZ-0101` | `ClaimAmountExceedsLimitError` | 报案金额超过年度上限 | `9` |
| `BIZ-0102` | `NegativeClaimAmountError` | 报案金额为负 | `9` |
| `BIZ-0103` | `InvalidDeductibleError` | 免赔额非法 | `9` |
| `BIZ-0104` | `InvalidRatioError` | 赔付比例非法 | `9` |
| `BIZ-0201` | `ReconciliationMismatchError` | 对账不一致（供库调用方主动抛出） | `9` |
| `DAT-0001` | `DataException` | 数据异常基类 | `1` |
| `DAT-0101` | `FileNotFoundError` | 输入文件不存在 | `1` |
| `DAT-0102` | `InvalidColumnError` | 缺少必需列 | `1` |
| `DAT-0201` | `DataValidationError` | 单字段/单行校验失败（**不抛出，收集用**） | — |
| `SYS-0001` | `SystemException` | 系统异常基类 | `2` |
| `SYS-0101` | `IOFailure` | 读写 Excel 失败 | `2` |
| `SYS-0201` | `ConfigurationError` | 配置项非法 | `2` |
| `SEC-0001` | `SecurityException` | 安全异常 | `3` |

## 5. 配置

优先级：**环境变量 > `.env` > 代码默认值**。`.env` 不存在时会尝试加载 `.env.example`（方便第一次跑）。

| 分组 | 变量 | 默认 | 说明 |
| --- | --- | --- | --- |
| 路径 | `PROJECT_ROOT` | 源码根 | 容器内设为 `/app` |
| 应用 | `APP_NAME` | 保险理赔审计系统 | 显示名 |
| | `APP_ENV` | `development` | `production` 时 `is_production=True` |
| | `APP_DEBUG` | `true` | |
| 日志 | `APP_LOG_LEVEL` | `INFO` | |
| | `APP_LOG_FILE` | `logs/audit.log` | 相对 `PROJECT_ROOT` |
| | `APP_LOG_MAX_BYTES` | `10485760` | 10MB |
| | `APP_LOG_BACKUP_COUNT` | `30` | |
| 审计 | `AUDIT_ENABLED` | `true` | |
| | `AUDIT_LOG_FILE` | `logs/audit_trail.log` | |
| 数据 | `DATA_INPUT_FILE` | `sample_claim_data.xlsx` | 相对 `PROJECT_ROOT`，可给绝对路径 |
| | `DATA_OUTPUT_FILE` | `final_settlement_report.xlsx` | |
| | `DATA_OUTPUT_DIR` | `reports` | |
| | `DATA_PROFILE` | 空 | 映射 profile 的 JSON 路径；留空用内置 6 列标准表头 |
| 业务 | `INSURANCE_DEFAULT_DEDUCTIBLE` | `500` | |
| | `INSURANCE_DEFAULT_RATIO` | `0.80` | |
| | `INSURANCE_DECIMAL_PLACES` | `2` | `0~10` |
| | `INSURANCE_ANNUAL_LIMIT` | `500000` | |
| | `INSURANCE_POLICY_PREFIX` | `CL` | |
| | `INSURANCE_MIN_CLAIM_AMOUNT` | `0.01` | |
| | `INSURANCE_MAX_CLAIM_AMOUNT` | `99999999.99` | 必须大于最小值 |
| | `INSURANCE_TOLERANCE_ABSOLUTE` | `0.01` | 绝对容差（元） |
| | `INSURANCE_TOLERANCE_RATIO` | `0.001` | 相对容差，取「报案金额 × 该比例」 |
| | `INSURANCE_MINOR_THRESHOLD` | `1.00` | 轻微差异上限（元） |
| | `INSURANCE_MATERIAL_THRESHOLD` | `100.00` | 重大差异下限（元），必须大于轻微阈值 |

**容差规则**：单条记录的容差为 `max(INSURANCE_TOLERANCE_ABSOLUTE, 报案金额 × INSURANCE_TOLERANCE_RATIO)`。
`|差异| < 容差` 记「一致」；否则按 `|差异|` 分级：≤ 轻微阈值记「轻微」，< 重大阈值记「一般」，≥ 重大阈值记「重大」。

配置在进程启动时读取一次（`Settings` 单例）；`--input` / `--output` 优先级高于配置。非法配置抛 `ConfigurationError`（`SYS-0201`），退出码 `2`。

## 6. CLI

```
insurance-audit [--generate-mock] [--input PATH] [--output PATH]
                [--json] [--json-out PATH] [--manifest PATH]
                [--fail-on any|material|parse-error|none]
```

- `--json`：JSON 摘要输出到 stdout（日志走 stderr）；
- `--json-out PATH`：同一份摘要同时落盘；
- `--manifest PATH`：输出审计清单（输入 SHA256、字节数、工具版本、关键配置）；
- `--fail-on`：闸门策略，默认 `any`（有任何异常或解析失败即退出 1），可选 `material` / `parse-error` / `none`，含义见 §4.1。

`--help` 不初始化日志、不创建目录，可在只读环境执行。

读取层另有一个独立入口，专门做「接入前准备」：

```
python -m insurance_audit.data.reader [--print-template [--full] [--format xlsx|csv]
                                       [--out PATH] [--profile PATH]]
                                      [--init-profile [PATH] [--from FILE] [--skiprows N]]
                                      [--inspect FILE [--skiprows N]]
```
